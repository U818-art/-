# U818 Article Studio｜記事管理システム設計書 v1.0

## 0. 設計の前提（元動画の②③との違い）

元動画の「量産・自動投稿システム」をそのまま作らない理由：

1. **noteに公式投稿APIは存在しない**（公式ヘルプ明記・公開予定も未定）。
   非公式API・ブラウザ自動操作による投稿は規約リスク・
   アカウントBANリスク・仕様変更で突然壊れるリスクがある
2. U818の現在の投稿量（月数本〜十数本）に対し、
   18項目のフル自動化は過剰投資。開発時間が記事執筆と
   櫻紫下半期鑑定の制作時間を食う
3. U818の価値は「量産」ではなく文体・信頼・ブランド一貫性。
   量産システムはむしろブランド毀損リスク

**→ 設計方針：「下書き完成までを自動化・管理し、公開の30秒だけ手動」**
これが規約的に安全で、実務上も最も費用対効果が高い。

## 2. Phase 0：フォルダ＋テンプレ運用（今すぐ・開発不要）

```
U818-articles/
├── 00_ideas/          ← テーマメモ（1行でもOK）
├── 10_drafts/         ← 執筆中
├── 20_review/         ← リライト・品質チェック待ち
├── 30_ready/          ← 公開待ち（コピペするだけの状態）
├── 90_published/      ← 公開済みアーカイブ
├── _templates/
│   ├── essay.md       ← エッセイ系テンプレ
│   └── guide.md       ← 実用ガイド系テンプレ
└── _prompts/          ← リライトプロンプト等
```

### 記事ファイルの冒頭に付けるメタ情報（front matter）

```yaml
---
title: （タイトル）
type: essay | guide
status: idea | draft | review | ready | published
paid: free | paid
price: 0
tags: []
published_url:
published_date:
checklist:
  地名チェック: false
  AIっぽさ除去: false
  スタイル準拠: false
  タイトル3案比較: false
  タグ設定: false
---
```

ファイル名規則：`YYYYMMDD_type_タイトル短縮.md`
例：`20260706_guide_AI画像プロンプト比較.md`

**これだけで元動画②の「記事データベース管理・下書き保存・投稿キュー・投稿履歴」の実質的な代替になる。**

## 3. Phase 1：ローカル管理アプリ（Claude Codeで構築）

### 3.1 構成

- ローカルWebアプリ（Netlify不要・自分のPCでのみ起動）
- データはPhase 0のMarkdownファイルをそのまま読む
  （＝アプリが壊れてもデータは無事。ロックインなし）

### 3.2 機能（優先順）

**必須（Day 1で作る）**
1. ダッシュボード：全記事のステータス一覧（idea→published のカンバン表示）
2. 品質チェック実行：Claude APIに記事＋チェックリストを渡し、
   - 地名・特定情報の検出（最重要・NG箇所を行番号で指摘）
   - AIっぽい定型表現の検出
   - スタイル準拠判定（essay/guide規則との照合）
   を自動レポート
3. リライト実行：v1リライトプロンプトをAPI経由で適用し、
   差分表示（元→後の比較）

**あると良い（Week 2以降）**
4. タイトル・タグ・冒頭3行の複数案生成
5. 公開用コピーボタン（note貼り付け最適化済みMarkdownを整形）
6. 実績記録：公開後のスキ数・ビュー数を手入力→簡易グラフ

**作らない機能（明示的に除外）**
- 自動投稿（規約リスク）
- 自動リサーチの完全放置運転（品質統制不能）
- 競合分析の常時クローリング（必要時にClaudeに都度依頼で十分）

### 3.3 品質チェックのプロンプト仕様（アプリに組み込む判定基準）

```
以下の記事を5項目で監査し、JSON形式で返してください。
1. privacy: 居住地・地名など書き手特定につながる記述の有無
   （セブ・マニラ等の過去海外在住地は除外）→ 検出箇所を引用
2. ai_smell: AIっぽい定型表現のリスト（該当文を引用）
3. style: type（essay/guide）のスタイル規則との不一致点
4. opening: 冒頭3行の離脱リスク評価（高/中/低と理由）
5. paid_ready: 有料販売品質か（paid記事のみ／具体性・上乗せ価値）
```

## 4. Phase 2：マルチプラットフォーム展開（元動画③相当）

**着手条件：Brain または Tips への展開を実際に決めたら。それまで作らない。**

- 設計はプラグイン方式の思想だけ先取り：
  Phase 0のfront matterに `platforms: [note]` を追加しておけば、
  将来 `[note, brain, tips]` に増やすだけで拡張できる
- プラットフォーム別の差分は「価格表記・導入文・タグ形式」程度なので、
  変換プロンプトを _prompts/ に1枚追加すれば実質対応可能
  （フル開発は不要な可能性が高い）

---

## 5. 優先順位に関する率直な助言

1. **今週やる**：Phase 0のフォルダ作成（30分）＋リライトプロンプトv1の試運転（既存記事1本で）
2. **やらない**：Phase 1の開発着手。理由＝櫻紫下半期鑑定（7〜12月対象）は
   販売可能期間が毎週縮む在庫。システム開発は期限が縮まない。
   期限がある方が常に先
3. **鑑定リリース後**：Phase 1をClaude Codeで半日構築。
   このとき本設計書をそのままClaude Codeに渡せば要件定義として機能する
